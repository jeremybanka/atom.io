# against useEffect

Components observe state and express intent. Put derivation in selectors, commands
in event handlers or transactions, asynchronous reads in `Loadable` states, and
ongoing synchronization in atom effects. Enable
[`atom.io/ban-use-effect`](/docs/eslint-plugin#ban-use-effect) to enforce this
boundary in application code.

`useLayoutEffect` remains appropriate for measuring or changing committed layout
before paint. It is not an escape hatch for ordinary synchronization.

These twenty comparisons distinguish harmful React patterns, valid React effects
that belong elsewhere in atom.io, and recommended alternatives.

Exhibits use the implicit store; your controller supplies exported inputs. With an
explicit Silo, use that Silo’s operations: module-level state operations do not
follow `StoreProvider`.

Atom-effect cleanup runs on atom disposal, not component unmount. Resource
examples use explicit ownership or `useAtomicRef`, which publishes the host node
and clears it on cleanup. Their hosts stay mounted for the component’s lifetime.
Use one presentation owner per key; readers can share state without owning its
resources. Dispose unused family members when their owning model ends, not when
one reader unmounts.

Keep DOM handles out of persistence, server snapshots, and undo history. The
shared [services](https://github.com/jeremybanka/atom.io/blob/main/packages/atom.io/docs/source/exhibits/react/effects/services.ts),
[helpers](https://github.com/jeremybanka/atom.io/blob/main/packages/atom.io/docs/source/exhibits/react/effects/helpers.ts),
and [views](https://github.com/jeremybanka/atom.io/blob/main/packages/atom.io/docs/source/exhibits/react/effects/views.tsx)
are application code, not atom.io APIs; their implementations ship with the
exhibits.

<span data-effect-verdict="harmful">Harmful</span> Chain effects to complete one action

Chaining effects spreads one game action across renders and creates intermediate states. A reducer or one event handler can calculate the transition in ordinary React.

<EffectCluster verdict="best-practice">

## maintaining an autosaved draft

A draft should save after 400 milliseconds without an edit, including edits originating outside the editor.

<EffectCluster verdict="react-only">

<Exhibit src="react/effects/06-autosave-before-tie-autosaving-to-component-lifetime.tsx" soft />

<span data-effect-verdict="react-only">With React.useEffect</span> Tie autosaving to component lifetime

This is ongoing synchronization with storage. `createAutosaver` debounces edits for 400 milliseconds, serializes writes, and ignores obsolete completion messages. The component owns that helper and cancels unsent work when its scope ends. The initial `null` text means no edit has occurred, so mounting alone does not save an empty draft.

</EffectCluster>

<EffectCluster verdict="best-practice">

<Exhibit src="react/effects/06-autosave-after-let-the-draft-own-its-saves.tsx" />

<span data-effect-verdict="best-practice">Best practice</span> Let the draft own its saves

Create the same autosaver in the draft’s atom effect, schedule it on text changes, and ignore its own status updates. Writes are serialized per draft instance so a slower earlier write cannot finish after a newer one. The draft now owns the process: unmounting the editor does not discard a pending save. Disposing a member of `draftAtoms` cancels pending work and suppresses completion updates; it cannot undo a request already sent. A production multi-client editor also needs server-side conflict/version handling. A failed save is displayed; an explicit retry policy can be added at the same state boundary.

</EffectCluster>

<EffectCluster verdict="best-practice">

## debounced search

Typing should update the input immediately while postponing a search until the query settles.

<EffectCluster verdict="react-only">

<Exhibit src="react/effects/08-debounce-before-debounce-requests-inside-the-search-component.tsx" soft />

<span data-effect-verdict="react-only">With React.useEffect</span> Debounce requests inside the search component

</EffectCluster>

<EffectCluster verdict="best-practice">

<Exhibit src="react/effects/08-debounce-after-let-query-state-own-the-debounce.tsx" />

<span data-effect-verdict="best-practice">Best practice</span> Let query state own the debounce

Separate live input, settled query, and query-keyed results. An atom effect owns the delay and Loadable family members own requests. Once started, a request may finish into its own cache entry even if the user moves on. The search session, rather than an individual input component, owns the timer.

## polling a remote job

A job’s progress should refresh once a second until completion, without overlapping requests, while its presentation owner is attached.

<EffectCluster verdict="react-only">

<Exhibit src="react/effects/09-polling-before-run-the-polling-loop-inside-the-view.tsx" soft />

<span data-effect-verdict="react-only">With React.useEffect</span> Run the polling loop inside the view

Polling synchronizes with a remote process. `pollJob` waits for each request before scheduling another and stops on completion or failure. It returns cleanup that stops the timer, aborts the current read, and suppresses late outcomes. The component effect owns that cleanup here.

</EffectCluster>

<EffectCluster verdict="best-practice">

<Exhibit src="react/effects/09-polling-after-give-each-job-an-explicit-polling-owner.tsx" />

<span data-effect-verdict="best-practice">Best practice</span> Give each job an explicit polling owner

A host-node family member owns each polling session and a Loadable family member owns its result. `useAtomicRef` publishes the output node and clears it on cleanup. The effect starts on attachment, aborts on detachment, and schedules only after a request finishes. For polling that should outlive the view, use explicit controller-owned activation state instead. This exhibit assumes one presentation owner per job ID; additional progress displays should only observe the result.

</EffectCluster>

<Exhibit src="react/effects/11-store-before-copy-an-external-store-into-local-state.tsx" soft />

Reading a snapshot into local state and later subscribing can miss changes between those steps. For an existing external store, React provides `useSyncExternalStore` and its server-snapshot protocol.

<span data-effect-verdict="best-practice">Best practice</span> Observe the source of truth with `useO`

<EffectCluster verdict="best-practice">

<Exhibit src="react/effects/12-connection-after-let-connection-state-own-the-socket.tsx" />

<span data-effect-verdict="best-practice">Best practice</span> Let connection state own the socket

Keep the host node and received messages in separate keyed atoms. `useAtomicRef` publishes attachment; the host’s atom effect opens and closes the socket. <Exhibit src="react/effects/18-analytics-after-record-explicit-presentation-transitions.tsx" />

<span data-effect-verdict="best-practice">Best practice</span> Record explicit presentation transitions

Publish the screen’s host node with `useAtomicRef` and let the atom effect report its transition from absent to present. The initial server and hydration output must match before revealing a browser-stored display name.

<EffectCluster verdict="react-only">

<Exhibit src="react/effects/19-hydration-before-track-hydration-with-a-mount-effect.tsx" soft />

<span data-effect-verdict="react-only">With React.useEffect</span> Track hydration with a mount effect

A mount effect is a documented way to switch to client-only content, although the extra rendering phase should be used sparingly.

</EffectCluster>

<EffectCluster verdict="best-practice">

<Exhibit src="react/effects/19-hydration-after-match-hydration-through-server-and-client-snapshots.tsx" />

<span data-effect-verdict="best-practice">Best practice</span> Match hydration through server and client snapshots

Put the browser-backed value in an atom and use React’s external-store snapshot protocol to distinguish hydration from ordinary client rendering. ## judging a replacement

A replacement should identify what starts work, what stops it, and what must
already have committed. React can preserve state while disconnecting effects in a
hidden `Activity` boundary. Attachment-based ownership, viewport-based ownership,
and application-owned resources are different policies; choose the signal that
matches the intended behavior instead of assuming atom lifetime is view lifetime.

These judgments build on React’s guidance on
[unnecessary effects](https://react.dev/learn/you-might-not-need-an-effect),
[events and effects](https://react.dev/learn/separating-events-from-effects),
[synchronization and cleanup](https://react.dev/learn/synchronizing-with-effects),
[fetching and hydration](https://react.dev/reference/react/useEffect),
[external stores](https://react.dev/reference/react/useSyncExternalStore),
[DOM refs](https://react.dev/learn/manipulating-the-dom-with-refs),
[layout effects](https://react.dev/reference/react/useLayoutEffect), and
[Activity](https://react.dev/reference/react/Activity).
