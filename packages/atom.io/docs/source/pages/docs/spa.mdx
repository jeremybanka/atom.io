# <low-emphasis>@atom.io</low-emphasis><wbr />/spa

Start with the [SPA + Astro SSR template](https://github.com/jeremybanka/atom.io/tree/main/templates/spa-astro-ssr) for a ready-to-run application with server-rendered islands, resumable initial data, and typed database refreshes:

<Exhibit src="spa/exhibits/create-astro-template.sh" />

The initializer installs the project dependencies. The template includes Astro, SPA, atom.io, resumability, SQLite, and tRPC. Its README covers the Node environment, database setup, and production commands. Read the [Astro integration guide](/docs/spa/astro) to see how the pieces fit together.

SPA is a JSX framework built around atom.io. Components run once per mounted instance; atom.io owns state, selectors, transactions, and timelines. Expressions in JSX update the affected DOM when the state they read changes. This is an experimental framework with its own lifecycle API.

## build from scratch

If you prefer to assemble your application, install SPA and its state-engine peer:

<Exhibit src="spa/exhibits/install.sh" />

Then choose [@atom.io/spa/astro](/docs/spa/astro) for Astro islands or [@atom.io/spa/vite](/docs/spa/vite) for a standalone Vite application. The Astro integration includes SPA's JSX compiler; a Vite application registers the compiler plugin directly.

For the view APIs, jump to [rendering](#rendering) or [hooks](#hooks).

## a reactive view

Capture getters and setters during component setup, naming each after its atom: pointAtom uses getPoint and setPoint. Call the getter inside JSX to make that DOM expression reactive:

<Exhibit src="spa/exhibits/point.tsx" />

The point is one atom containing an object. Each coordinate expression reads the same point accessor; an atom update reevaluates both expressions, and unchanged primitive results skip DOM writes. There is no separate subscription to each object field. Reusable or multi-atom derivations belong in atom.io selectors.

The component body runs once. A read during setup captures a snapshot; a read inside JSX participates in dependency tracking. Event handlers read the current value without subscribing. Helper functions called from JSX can read accessors too: their reads belong to the current DOM computation.

Props remain live through getters. Destructuring them during setup captures their current values. Hook token arguments are fixed for a mounted instance; use a new keyed component instance when its token must change.

Component children follow the same getter contract as named props. A component declaring string children reads a string for both literal text and expression children, including an explicit children attribute. Read props.children inside compiled JSX or a tracked binding for reactive updates; setup reads capture a snapshot. Deliberately function-valued children remain functions, including render callbacks.

## rendering

Astro handles rendering and hydration for its islands. These APIs are for application shells, standalone Vite entrypoints, and custom server rendering.

### render

Mount a component into an existing host. This widget returns a cleanup function for the shell to call when it removes the counter:

<Exhibit src="spa/exhibits/rendering/render.tsx" />

render returns dispose and flush methods. dispose removes the owned DOM and releases subscriptions and cleanup callbacks; atom.io state outlives the view. Updates coalesce in a microtask, and flush applies pending DOM work immediately.

### hydrate

Attach a component to matching server-rendered HTML. This form field uses the same component and ID prefix as the server example below:

<Exhibit src="spa/exhibits/rendering/hydrate.tsx" />

hydrate preserves matching elements, attaches events, and restores reactive subscriptions. It accepts the same options as render and returns the same dispose and flush methods. Initial state, component structure, and IDs should agree. If they differ, SPA logs one readable warning per root in development and production and repairs the affected markup while continuing hydration. Component setup runs once and the view stays interactive. Matching DOM is reused; replaced nodes can lose focus or unsaved input.

Hydrating HTML does not transfer an atom.io store from the server. For server-produced data that becomes the browser's initial state, see [resumability with Astro](/docs/spa/astro#resumability).

### renderToString

Produce the HTML that your server inserts into the form's host element:

<Exhibit src="spa/exhibits/rendering/render-to-string.tsx" />

EmailField uses [useId](#useid) to connect its label and input. The signup prefix keeps those IDs consistent with the hydration example. Give separate roots distinct prefixes.

renderToString runs synchronously, retains no subscriptions, and omits onMount callbacks. When a component reads state, supply its prepared, request-specific store in the options and restore matching values before browser hydration. It does not await promises or serialize state implicitly.

### Fragment

Return related fields without adding a wrapper inside the surrounding form:

<Exhibit src="spa/exhibits/rendering/fragment.tsx" />

The fragment syntax uses the Fragment export automatically. A Fragment groups its children without introducing a DOM element, a store, or a separate component lifetime.

Call setup helpers synchronously during component setup or owned mount callbacks, then capture their results for event handlers. DOM computations should only read state. Use event handlers and atom.io transactions for writes.

### useGetter

Name the accessor after its token, such as cartCountAtom and getCartCount. Calls inside JSX subscribe that DOM computation. Calls during setup capture a snapshot; event handlers read the current value without subscribing.

### useSetter

<Exhibit src="spa/exhibits/hooks/use-setter.tsx" />

The writer stays stable for the mounted instance and accepts either a replacement value or an updater function. It does not subscribe to state.

### useLoadable

<Exhibit src="spa/exhibits/hooks/use-loadable.tsx" />

Call the returned accessor inside JSX. It retains the last observed value during refreshes; errors declared by the token appear in error when a fallback is supplied. See [async state](#async-state) for the result shapes and family behavior.

In Astro, mount this browser-fetching component as a client-only island. For data fetched during server rendering, use [resumability](/docs/spa/astro#resumability).

### useTimeline

Bind history controls to a document's timeline. Mount this button beside an editor that writes noteAtom:

<Exhibit src="spa/exhibits/hooks/use-timeline.tsx" />

useTimeline returns stable undo, redo, and clear commands plus tracked getCursor and getLength readers. Reads inside JSX update the controls as history changes. The methods may be destructured without losing their store binding.

For transaction groups, getTransaction returns optional undo and redo callbacks for the adjacent groups. Retrieve and invoke the current action together, or retain a callback to keep its captured target. Group travel applies across participating timelines that still share the relevant history head, leaving diverged timelines unchanged.

### useTransaction

Bind a transaction while preserving its arguments and return value. This command adds an item and opens the cart in one transaction:

<Exhibit src="spa/exhibits/hooks/use-transaction.tsx" />

Capture the command during setup and invoke it from an event handler. useTransaction accepts a transaction token, not a transaction family.

### useDisposal

Call useDisposal() without arguments during component setup to capture the current root's store. The returned disposer accepts a family and key or an existing family-member token, just like atom.io's disposeState. Capture it for event handlers or onCleanup; it remains bound to that store when called later.

<Exhibit src="spa/exhibits/hooks/use-disposal.tsx" />

This toggle owns its menu visibility member. Its ID must be unique among owners of that family in the same store. If the menu panel is a separate consumer, keep both under a common owner and register disposal there, as in [ambient UI state](#ambient-ui-state-and-ownership). Disposing one consumer must not remove state still used by another. Only family members can be disposed; standalone atoms remain in their store.

### useRef

The callback receives the element on attachment. On cleanup, SPA clears the atom only while this attachment still owns the reference. useRef also accepts a family token and key.

### useId

The ID is stable for this component instance. Server rendering and hydration use the same root prefix and component structure so generated IDs agree.

### onMount

<Exhibit src="spa/exhibits/hooks/on-mount.tsx" />

onMount runs once for the mounted instance and does not run during server rendering. Register teardown with onCleanup when the work acquires a resource.

### onCleanup

Release work when its owning view goes away. This page restores the previous document title when removed:

<Exhibit src="spa/exhibits/hooks/on-cleanup.tsx" />

The mount callback owns browser-only setup, and onCleanup registers its teardown with that owner. Cleanup also runs when a keyed component is removed or its root is disposed. For family members owned exclusively by an instance, see [ambient UI state](#ambient-ui-state-and-ownership). Use the same pattern for listeners, observers, and timers.

### useStore

Capture the root's store for a store-aware operation. This button copies the draft from the same store the view is using:

<Exhibit src="spa/exhibits/hooks/use-store.tsx" />

useStore returns the supplied render/hydrate store, the selected Astro island store, or the implicit store. It creates no store or subscription. Capture it during setup or an owned onMount callback. Direct getFromStore reads do not subscribe JSX; useGetter and useLoadable provide tracked reads.

## families

useGetter, useSetter, useRef, and useTimeline also accept a family token and its key. useLoadable accepts a family, key, and optional fallback. All five resolve members in the component's store and preserve the declared key type.

<Exhibit src="spa/exhibits/families.tsx" />

Keys are captured during component setup. To select another member, replace the instance in a reactive child collection using a new application key. The previous instance releases its subscriptions and refs. useTransaction takes a transaction token; atom.io has no transaction-family token.

### Ambient UI state and ownership

Ambient state is useful for ephemeral UI flags that several components need to read or change, such as whether a popover is open. Define the family at module scope and give each popover an application identity. Its trigger and panel can bind to the same boolean without passing the value and setter through their parent.

This exhibit gives each toolbar its own formatting and keyboard-shortcut help popovers. Hiding formatting help removes its keyed instance and disposes its visibility state. Showing it again starts closed; the shortcuts popover and other toolbars keep their state:

<Exhibit src="spa/exhibits/state-lifetimes.tsx" />

The reconciliation key identifies a component among siblings. The family key identifies application state across the whole store: the tuple includes both the toolbar ID and help topic so separate toolbars do not share visibility by accident. The toolbar ID must be unique within that store. The renderer consumes key; pass the state identity as an ordinary prop.

Call useDisposal() without arguments during setup. It captures the current root's store and returns atom.io disposal, accepting either a family and key or an existing member token. Invoke it from an event handler or register it with onCleanup. It works with the implicit store, render/hydrate options.store, and isolated Astro stores without passing a disposal callback through props. Custom stores still need the module-scope definitions installed through Silo.install.

HelpPopover owns the visibility member shared by its trigger and panel, so it disposes that member after both consumers are removed. A single consumer must not dispose state that other live consumers still need. Shared session or application state belongs to the owner that knows when every consumer has finished. Standalone atoms persist for their store's lifetime; disposal removes family members, not standalone atoms.

Getter and setter bindings capture their family key during setup. Replacing a keyed instance changes its binding; changing an identity prop on an existing instance does not rebind it. Disposing a family member removes its stored value and resources; a later read recreates it from its default. Keep user-authored content in state whose owner matches its intended persistence, rather than treating it like a popover's transient visibility.

## async state

Call useLoadable during setup, then call its accessor inside JSX. Without a fallback, it returns LOADING until it observes a settled value; afterward it returns loading and value, retaining the last observed value during refreshes. With a fallback, it always returns an object and exposes errors declared in the token's catch option through a separate error property. The fallback and error remain visible during retries. Without a fallback, handled errors appear in value. Explicit null and undefined fallbacks are supported when permitted by the token's type.

Readable families take a fixed key as the second argument and an optional fallback as the third. Each accessor retains only its own member's last observed settled value. Replacing a keyed component creates a new accessor, which starts with its fallback or LOADING if that member is pending. Atom.io owns promise settlement; SPA does not fetch, retry, cancel, or suspend rendering. Server rendering returns the current view immediately without awaiting promises.

## boundaries

SPA does not provide React compatibility, an independent signals graph, or React-style state and effect hooks. Async components, promise children, suspense, portals, style objects, and error boundaries are outside the current feature set. Model asynchronous work in atom.io and render its state through synchronous JSX.

Development uses full page reloads rather than preserving component state across edits. The runtime targets modern browsers with ES2022 and DOM Range support.
