# realtime component reference

This page maps the public realtime surface by responsibility. Use the linked
guides for composition and lifecycle; use this inventory when you know the
problem and need to find the owning package.

Types, protocol constants, event names, limit types, rejection codes, and
envelope validators are exported beside the functions listed here.

For exhaustive entrypoint inventories, use the package pages for
[`atom.io/realtime-client`](/docs/realtime-client),
[`atom.io/realtime-react`](/docs/realtime-react),
[`atom.io/realtime-server`](/docs/realtime-server), and
[`atom.io/realtime-testing`](/docs/realtime-testing).

## <low-emphasis>atom.io</low-emphasis>/realtime-client

### rigid clients

- `pullAtom` and `pullAtomFamilyMember`
- `pullMutableAtom` and `pullMutableAtomFamilyMember`
- `pullSelector` and `pullSelectorFamilyMember`
- `pushState`
- shared client state for the authenticated socket/user and subscriptions

Every pull/push function accepts an explicit Store and socket and returns a
disposer.

### Atomic Mosaic client

- `syncMosaic` creates a Store-owned `MosaicController`.
- `MosaicController.change` prepares and queues model intent.
- `publishPresence` sends ephemeral model presence.
- `synchronize`, `retryPending`, and `clearProblem` expose recovery controls.
- `createGroupId` gives several operations one stable history gesture.
- the sync-state atom exposes status, revision, pending ids, presence, and problem.

## <low-emphasis>atom.io</low-emphasis>/realtime-server

### connection, rigid state, and rooms

- `realtime` authenticates Socket.IO and owns connection cleanup.
- `realtimeStateProvider` serves rigid state.
- `realtimeStateReceiver` accepts validated leased publications.
- mutable and family providers serve transceiver-backed rigid state.
- `provideRooms`, `spawnRoom`, and room providers host isolated room processes.
- IPC socket components connect parent and room processes.

### Atomic Mosaic server

- `defineMosaicAtomRegistration` binds a mutable token, transceiver class,
  operation schema, optional key/presence schema, and checkpoint policy.
- `createMosaicServer` authorizes and hosts registered Mosaic atoms.
- `MosaicStorageAdapter` defines append, recover, checkpoint, session, and
  retention behavior.
- `InMemoryMosaicStorage` is the test/reference adapter.

## lifecycle rule of thumb

Declarations and model classes are usually module-lifetime values. Activated
Domains, servers, controllers, connections, leases, subscriptions, binders,
rooms, and test fixtures own resources and must be disposed. Storage adapters
may outlive a server restart; Store projections and presence generally should
not.

When an API returns a function or exposes `dispose`, treat cleanup as part of
the correctness contract, not optional housekeeping.
