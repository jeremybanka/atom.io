# Mosaic Text

Atom.io provides two complementary text representations. Choose according to
the size and residency requirements of the document, not according to the UI
framework.

The canonical Markdown editor composes the two concerns with a bounded text
index, partial residency, projections, Domain history, and checkpoints.

## logical runs and positions

The logical-run model stores each insertion as a stable logical run. Physical
checkpoint fragments may split that run without changing its identity.
Positions use a run id, grapheme offset, and affinity; they do not use a fragile
whole-document UTF-16 offset.

<Exhibit src="realtime/prepare-logical-text-edit.ts" />

This model makes concurrent descendants and actor-selective compensation
possible. Undo emits a history operation against retained operation ids instead
of replacing the document with a previous snapshot.

## bounded indexes

Long documents need a physical index in addition to the logical edit model.
Mosaic Text indexes use bounded leaf, node, and alias members. Readers resolve
UTF-16, grapheme, line, and range queries logarithmically and can recover from a
stale leaf identity after a split or merge.

<Exhibit src="realtime/index-bounded-text.ts" />

Index maintenance belongs in the same accepted Domain batch as the source edit.
A source revision and an index revision that can diverge are not a correct
partial-residency system.

## range projections

The headless projection controller acquires a root summary and only the range
members required for a viewport plus overscan. It creates ordinary selectors
for exact resident leaves and shares leases when consumers overlap.

<Exhibit src="realtime/project-a-mosaic-text-viewport.tsx" />

`useMosaicTextRange` owns React acquisition and release lifecycle. It retains
the last complete viewport while a replacement observer is acquired, reconnects
after residency returns, and ignores incomplete cuts. Parsing, layout, syntax
highlighting, and rendering should consume that bounded projection rather than
materializing the full document.

## editor lifecycle

<Exhibit src="realtime/edit-a-mosaic-text-projection.tsx" />

`useMosaicTextEditor` owns the coordination that must be identical across
renderers: the optimistic draft, IME state, contiguous logical edit, local
selection anchors, remote selection reprojection, commit delay, and the point
at which a complete accepted cut replaces the draft. It deliberately keeps the
last proven text and selections when residency or presence arrives ahead of the
members needed to resolve them.

The renderer owns native input and geometry. It reports the editor's complete
visible string and selection offsets to the hook, applies the selection returned
by the hook, and draws returned collaborator ranges against the same returned
string. It must measure logical attributes and geometry in one layout cut so a
new coordinate cannot be painted with an old rectangle.

Application composition owns identity, permissions, status labels, viewport
policy, and the calls that publish presence or submit a replacement. It should
not implement another draft queue, cursor transform, or projection fallback.
This boundary is more important than minimizing the number of template lines;
a short template should be the consequence of using the core contracts.

## content-addressed text roots

A content-addressed text root contains a generation and a reference to a bounded
tree of immutable branch and leaf objects. Bulk import streams grapheme-safe
chunks. Local replacement path-copies only touched leaves and their branch path.

The staging sequence is:

1. stream or path-copy immutable text objects into unreachable checkpoint storage;
2. verify content keys, graph shape, bytes, depth, object count, deadline, and cancellation;
3. create a proposal protection for the staged external root;
4. accept one small Domain operation that publishes the root; and
5. have the next Domain checkpoint adopt the accepted root before releasing proposal protection.

A crash between acceptance and checkpoint must not let garbage collection erase
the newly authoritative text. A rejected or abandoned proposal must eventually
expire and become collectible.

## checkpoints and structural sharing

<Exhibit src="realtime/checkpoint-a-domain-incrementally.ts" />

Domain checkpoints store a small atomic root and content-addressed member and
index objects. The content-addressed text representation contributes an external
root dependency. Unchanged text objects are structurally shared; a local edit
persists the new leaf/path/root rather than another full document.

History compaction, outboxes, sessions, proposals, presence anchors, and active
readers may all protect revisions or operation ids. Garbage collection traces
every retained root and advances a retention epoch only after a fenced sweep.

## Unicode boundaries

Public selections are grapheme-aware. Before applying a raw UTF-16 browser
selection, resolve each endpoint through the text reader with an explicit left
or right affinity. This prevents edits from splitting surrogate pairs,
combining sequences, or emoji joined by zero-width joiners.

Presence carries these logical positions, never raw viewport offsets. Resolve a
collaborator against the same projection cut used to render the text. If the
run or boundary is not resident yet, retain the last proven selection or omit it;
do not clamp it to document start/end or reinterpret it in a different cut.

Keep a bounded maximum for one grapheme and for one edit. Unicode correctness is
not permission to accept an unbounded string as one operation.

## limits that belong in the design

Enforce and test limits for:

- inserted bytes and runs per operation;
- deletion intervals and history targets;
- leaf UTF-16 units, graphemes, and fragments;
- branch fanout, tree depth, and alias generations;
- resident ranges, members, bytes, and object reads;
- staged objects, updates, bytes, object depth, deadline, and cancellation;
- checkpoint objects, tail batches, retained actions, receipts, and sessions;
- parser input, rendered blocks, overscan, and queued local drafts.

The package defaults are safety boundaries, not a capacity promise for every
deployment. Set tighter application limits where possible and run the actual
corpus and hardware profile you intend to support.

## reference implementation

The [Realtime Markdown editor](https://github.com/jeremybanka/atom.io/tree/main/templates/react-realtime-text-editor)
demonstrates logical edits, indexing, range residency, viewport projections,
actor-selective history, staged roots, restart, same-origin transport, and
large-corpus instrumentation. Its `INNOVATIONS.md` records the places where the
implementation had to establish new realtime contracts.
