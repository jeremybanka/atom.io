# Peer compatibility checks

The [root peer-check command](../package.json) runs each package's complete Breakage npm check through Turbo for local use. In the [Breakage workflow](../.github/workflows/breakage.yml), All Peer Eras Represented discovers the package configurations and every configured environment, then audits coverage of each declared peer compatibility era, support changes, and planned local releases. An unsuccessful audit blocks the environment matrix. Required peers must have relationship suites, and every environment must be auditable. The prologue builds and packs the candidates once and distributes the same archives to all matrix jobs.

Each matrix job exercises one environment and uploads a structured Breakage receipt even on assertion failure. Fail-fast is disabled. The final Peers check independently discovers the configured inventory again and requires exactly one passing receipt for every environment. It verifies the commit, candidate archive digests, package identity, installed peer identities, and complete relationship suite results. Missing, duplicate, unexpected, skipped, audited-only, failed, or malformed receipts fail the gate. A successful coverage audit alone never counts as test execution. The independent Public job runs the existing SDK and ESLint historical public-contract checks. Peers depends only on the coverage audit and environment matrix, so it can finish without waiting for Public. Both Peers and Public must pass for the workflow to succeed. Peer checks exercise the current packed API; they do not replace replaying contracts from a previous release.

Turbo builds and packs every participating package before checking it. The [task graph](../turbo.json) includes local peer archives, including both the SDK and React adapter for devtools. Checks are uncached because they inspect release tags, Changesets, package installation, and consumer execution. Package-owned representative manifests and pnpm lockfiles freeze the installed peers; preparation disables automatic peer installation and lifecycle scripts. Breakage's default npm installation installs candidate archives and their runtime dependencies inside each disposable stage, without automatically supplying peers.

Each integration owns its behavior suites under its own tests directory. The package's ordinary and public test commands select those suites; the SDK owns core and realtime cases. Portable consumer programs and declaration checks live in package-owned fixtures and are shared by ordinary package tests, packaging checks, and the peer matrix. ESLint reuses its existing consumer fixture rather than maintaining a second copy.

Each package can measure coverage of its own source. CI checks public coverage, retaining the SDK and React's existing 100% thresholds. Shared runner configuration and environment helpers live in repository scripts rather than another package's tests.

Contracts import consumer package names without source aliases. Framework contracts exercise store identity, state reads/writes, public declaration types, and the devtools stylesheet. Solid uses its public context provider; this does not establish the separate StoreProvider wrapper's behavior. ESLint contracts exercise all four rules and require typed public exports without installing authoring utilities into the consumer.

The [shared release policy](../scripts/breakage-peers.ts) assembles the actual release plan using Changesets’ published APIs, without the status command’s separate Git-diff audit. A pending version takes precedence over the workspace version. After versioning consumes the changesets, the current manifest is the exact target exercised by a coordinated build. This permits the versioning PR to run the same environments. Candidate results remain conditional on publication: the hook does not claim registry attestation, and metadata substitution does not rebuild embedded version constants. Released representatives continue to test the actual registry SDK independently.

SDK support is authored explicitly in each integration's manifest. Advancing the SDK's local version does not rewrite those ranges. A planned release outside declared support, a missing representative, a stale archive, changed frozen installation inputs, or conflicting physical peers fails the check. Breaking-support certification follows this repository's version policy: a minor or major release before 1.0, and a major release afterward. Certification cannot waive consumer assertion failures or missing planned peer coverage.

The ESLint check uses its existing scoped release tag. The React, Solid, and devtools configurations explicitly declare first publication because those packages were unavailable in the registry when this setup was added. Once published, verify the release commit, push the corresponding scoped tag, and replace each first-publication baseline with its scoped tag pattern before subsequent releases. Add ordinary released-contract replay for those packages once a release containing their contracts exists. Do not substitute a synthetic tag or treat a missing baseline as a passing historical check.

Breakage creates and removes the ignored test directory inside each representative. If a process is killed, inspect that directory and ensure its process has stopped before removing it. Normal failure paths clean their own stages. Never run two checks that select the same representative concurrently.
