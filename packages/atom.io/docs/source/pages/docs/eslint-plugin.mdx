# <low-emphasis>@atom.io</low-emphasis>/eslint-plugin

`@atom.io/eslint-plugin` provides rules for explicit state and transaction
declarations, typed errors, and React effect ownership.

## install

Install the plugin separately as a development dependency, alongside ESLint and
`typescript-eslint`. The plugin supports ESLint 9 and 10. Its TypeScript peer
describes the compiler API used by ESLint (4.8.4 through 6.0.x), rather than the
compiler you use to build your project.

For TypeScript 7 projects, install both compilers using
[TypeScript's recommended aliases](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/#running-side-by-side-with-typescript-6-0).
The starter templates use this setup:

<Exhibit src="tooling/eslint-plugin/install.sh" />

`@typescript/native` supplies TypeScript 7's `tsc` command for builds and type
checks. The `typescript` alias supplies the TypeScript 6 API that ESLint imports,
plus a separate `tsc6` command. Existing `tsc` scripts continue to use TypeScript 7.

## migrating from atom.io/eslint-plugin

Replace imports from `atom.io/eslint-plugin` with `@atom.io/eslint-plugin` and add the
new package to your development dependencies. The rule names, options, and
`atom.io` configuration namespace are unchanged. The SDK no longer ships the plugin
or declares ESLint and its parser as peers.

Why use `recommendedTypeChecked` instead of plain `recommended`?

`atom.io/exact-catch-types` needs TypeScript type information so it can compare an
atom's error type with its `catch` constructors. If you want a syntax-only ESLint setup,
use `typescript-eslint`'s plain recommended config and leave out
`atom.io/exact-catch-types`.

## rules

### ban-use-effect

`atom.io/ban-use-effect` bans React’s `useEffect` in application code. Enable it
explicitly for your application files; it requires no TypeScript type information.

<Exhibit src="tooling/eslint-plugin/ban-use-effect.config.ts" label="eslint.config.ts" />

The rule reports named imports (including aliases), reads through default or
namespace imports, destructuring, and value re-exports. It also tracks CommonJS
`require` when that global is configured in ESLint. It follows React bindings
rather than banning unrelated functions with the same name. Type-only imports
and exports are allowed, as is `useLayoutEffect` for committed layout work.

Every diagnostic points to [against useEffect](/docs/against-use-effect) and the
same guide installed at
`node_modules/atom.io/docs/agent/packages/against-use-effect.md`. Use those twenty
comparisons to choose between selectors, event handlers, transactions, atom
effects, and `Loadable` states. There is no automatic fix: choosing a replacement
requires understanding ownership and purpose.

Scope the rule to application code. Framework adapters implementing hooks and
documentation that demonstrates React effects may intentionally use `useEffect`.

### explicit-state-types

`atom.io/explicit-state-types` requires state declarations to include explicit type
arguments.

<Exhibit src="tooling/eslint-plugin/explicit-state-types.ts" />

This keeps important state types visible at the declaration site, where they are easiest
to audit.

### explicit-transaction-types

`atom.io/explicit-transaction-types` requires transaction declarations to include
explicit function type arguments.

<Exhibit src="tooling/eslint-plugin/explicit-transaction-types.ts" />

This keeps transaction inputs and outputs visible without having to inspect the
implementation.

### naming-convention

`atom.io/naming-convention` keeps declaration variable names and state keys aligned.

<Exhibit src="tooling/eslint-plugin/naming-convention.ts" />

For example, `countAtom` should use `key: "count"`, `historyTimeline` should use
`key: "history"`, and `saveTransaction` should use `key: "save"`. Families use
plural suffixes, so `userAtoms` uses `key: "user"` and `historyTimelines` uses
`key: "history"`. The same pattern applies to selectors and mutable atoms.

### exact-catch-types

`atom.io/exact-catch-types` checks that a state declaration's typed error channel
matches the constructors listed in its `catch` option.

<Exhibit src="tooling/eslint-plugin/exact-catch-types.ts" />

This helps prevent state from advertising that it may catch one error type while actually
catching another.
